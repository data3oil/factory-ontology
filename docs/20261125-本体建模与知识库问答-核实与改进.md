## 0 结论先说

1. **工程底子比预期好，问题不在代码质量，在评测口径。** 自带测试 `261 passed, 2 skipped`（18.6s）；
   规模探测显示问答耗时**线性**（21.4 万三元组：解析+建索引 1.79 s，问答 1.69 s），没有 O(n²)；
   `/api/ask` 已有按库上下文缓存，三处每次重建的路由都是 admin 重建入口，属于有意为之。
2. **最严重的一条：三套评测口径互相矛盾，谁都不能当结论。** 同一份 `food` 库，
   `eval_qa_baseline` 说 35/35 全对（1.0），`eval_hit_rate` 说 8/29（0.28）。
   而 1.0 的来源是**自证**——题库用的是引擎自己词典里的中文名，问答查的也是同一份名字。
3. **"换工厂只换域，原子代码不动"这句话，在问答层面目前没被证实。**
   原始表名/列名的问法下：valve 1.0（40 题）、auto_parts 1.0（25 题）、chem 0.64（28 题）、food 0.28（29 题）。
   两个 1.0 恰好是词典最贴的域，落差本身就是结论：**泛化没成立，是三个域各调了一遍词典。**

## 2 关键发现

### 2.1 三套评测口径，三个结论

| 口径 | 脚本 | food | chem | valve | 题源 |
|---|---|---|---|---|---|
| 基线评测 | `eval_qa_baseline.json` | **1.0**（35/35） | **1.0**（35/35） | **1.0**（39/39） | `eval_qa.gen_kb_questions`，用 `meta` 里的**中文实体名/属性名** |
| 命中率评测 | `eval_result_food/chem/valve.json` | **0.28**（8/29） | **0.64**（18/28） | **1.0**（40/40） | `eval_hit_rate.py`，用 **CSV 原始表名/列名** + 词典映射 |
| 消融实验 | `eval_ablation_valve.json` | — | — | a 0.045 / b 0.523 / c 0.727 | 同一份 nt、同一套题、只换词典 |

同一个仓库里同时存在 1.0 和 0.28，说明**至少有一套在测错东西**。看代码可以定案：
`eval_qa.py:225` 生成的问题形如 `"有多少%s%s" % (measure, cn)`，`cn` 与 `measure` 直接取自建库时的中文名，
而 `ontology_qa_v3.answer` 查的也是这份中文名 → 问句和答案共享同一套词，**这是自证，不是评测**。

`eval_hit_rate` 才是诚实的那套：它用台账里的原始表名/列名提问（如"batches有多少条记录"），
逼引擎自己去映射词典，于是暴露真实差距（food 0.28）。

### 2.2 评测记录缺归因字段，失败了没法定位

`eval_result_*.json` 的 `miss` 数组里，`expect`/`got`/`why` **全是 None**，只有题面。
也就是说：知道 food 掉了 21 题，但**掉在哪一步完全查不出来**——是词典没覆盖表名？属性没映射？聚合不支持？
这与平台侧"自造集恒 1.0"是同一类病：**结论不可归因，就不能改。**

### 2.3 域泄漏进了"通用"层

"换工厂只换域"的前提是通用代码里不该有域的东西，实测不是：

- `codes/api_server.py` 标题与描述写死 `食品企业知识库 REST API`，模块级 `QDATA = v3.build_data(v3.parse_nt(FOOD_NT), D)`；
  全文 `食品/valve/chem` 相关字样 **98 处**；
- `_CLEANUP_PATTERNS` 里留着 `valve2 / valve3 / valve9 / e2ecust / factory_multi_ / onb_` 这类**测试残渣名单**；
- 根目录 py 里 `valve` 出现 21 个文件、`食品` 9 个、`阀门` 11 个、`化工` 4 个；
- `codes/` 下 **36 个 `.bak*` 备份文件**（全仓 50 个）在版本控制里。

这些不直接影响问答，但对"开源算法原子层"的定位是硬伤：**别人拿去做第二个行业，第一眼看到的是食品 API。**

### 2.4 性能不是问题（这条要说清，免得白改）

规模探测（同一条问句，逐步放大三元组）：

| 倍数 | 三元组数 | parse+build (s) | answer (s) |
|---|---|---|---|
| 1× | 1 068 | 0.012 | 0.009 |
| 10× | 10 680 | 0.107 | 0.102 |
| 50× | 53 400 | 0.418 | 0.370 |
| 200× | 213 600 | 1.794 | 1.692 |

线性增长，无二次项。21 万三元组约 1.7 s/问，对中小工厂（实际都在 10 万以内）够用。
`api_server.py` 里 `_kb_ctx_cache`（587–665 行）已经按库缓存；1576/1759/1777 三处每次重建，
对应 `/api/admin/upload`、`/api/admin/rebuild`、`/api/admin/sync`——**重建本来就该重新解析，不是缺陷。**

### 2.5 健壮性一处：入参错形状抛裸 AttributeError

`ontology_qa_v3._field` 假定每条记录是 dict，传进去 list 时抛
`AttributeError: 'list' object has no attribute 'items'`（我用错 data 形状时实测触发）。
`answer(q, data, D)` 没有入参校验，外部集成方接到的是 Python 异常而不是可读错误。

## 3 全网/社区对照

| 主题 | 外部判据 | 对本仓库的含义 |
|---|---|---|
| 制造业本体复用 | IOF（Industrial Ontologies Foundry）2018 年选定 BFO 作上层；维护本体 IOF-Maint 对齐 ISO 15926-14（arxiv.org/pdf/2404.05224） | 自造顶层类可以，但**设备/工序/维护状态**这些概念已有 BFO 对齐的现成本体，至少该做标签映射，否则互通性为零 |
| 本体质量 | OQuaRE（基于 ISO/IEC 25000），可算 AROnto 属性丰富度、ANOnto 注释丰富度、LCOMOnto 内聚度等（github.com/astriduquer/oquare；PMC4141745） | 现在有 `ontology_quality.py`/`ontology_health.py`，但**没有对外可比的指标口径**。接 OQuaRE 的一组指标，本体质量才可跨库比较 |
| 图查询准确率 | CypherBench：小模型 31.4%、强模型 71.76%，失败是结构性的（方向写反、语法对但零行） | 受控查询 + 词典映射这条路，**70% 上下才是现实天花板**；food 0.28 说明词表没覆盖，不是"模型不行" |
| 语义层 vs 直写 | dbt 2026 基准：语义层 98.2%（Claude）/100%（GPT），直写 SQL 90%/84.1%，代价是覆盖率 | 本体/词典这条路方向对的，但**价值在覆盖率**，不在个别域的 100% |
| KG 在企业问答中的作用 | 企业 Text-to-SQL 场景下 KG 增强的对照基准（graphrag.com/appendices/research/2311.07509） | 别把"带证据"讲成"更准"；证据链解决的是**可核查**，不是准确率 |

工具链（rdflib / oxigraph / pySHACL）我**没有找到可直接引用的公开对比基准**，本机也没测，
所以不给"该换库"的结论——按"零依赖、单域、中小规模"的定位，自研解析在 21 万三元组下 1.8 s，
换库的收益无法证明大过引入依赖的代价。**这条明确列为不做**（见 §5）。

## 4 改进清单

### P0-1 评测口径收敛成一套，并加归因字段

- 删掉或明确标注 `eval_qa_baseline` 为"自证口径，不作能力证明"，只保留 `eval_hit_rate` 作对外数字；
- `miss` 每条补 `stage`（词典未命中/属性未映射/聚合不支持/数值不符）、`expect`、`got`；
- 对外 README 上的准确率，只能引用**原始表名列名提问**的口径。
- 验收：同一份 `eval_result_food.json` 里 21 条 miss 每条都有 `stage`，且按 stage 能算出分布。

### P0-2 建留出域（holdout）结果，把泛化讲成数字

`scripts/eval_holdout.py` 已经写好（self / public / pooled 三档词典对照），但**没有任何落盘结果**。
跑一次，把 `pooled − self`、`public − self` 写进 README。
- 验收：`scripts/eval_holdout_*.json` 存在，且报告中给出三个域的净增益，负值也照写（负迁移是要讲的事实）。

### P0-3 域泄漏清理

- `api_server.py` 的食品标题/描述/`FOOD_NT` 默认值改成按 kb 配置解析；
- `_CLEANUP_PATTERNS` 里的测试残渣名单移进测试夹具，不进产品代码；
- 26 个 `.bak_*` 移出仓库（本地留档即可），加 `.gitignore` 规则。
- 验收：`grep -c "食品\|valve\|chem" codes/api_server.py` 从 98 降到 0；仓库内 `.bak_*` 为 0。

### P1-1 入参校验

`answer()` 首行校验 `data` 形状，抛 `ValueError("data 必须是 {表名: [行dict]}")`。
- 验收：传 list 时得到中文可读 `ValueError`，不是 AttributeError。

### P1-2 接一组 OQuaRE 指标

至少 `AROnto`（约束/类）、`ANOnto`（注释/类）、`NOMOnto`（属性/类）。三行代码级改动，能跨库比较。
- 验收：`ontology_quality` 输出里出现这三项，且对 valve/chem/food 三库各跑一遍有数。

### P2 静态 50 条

`evidence_kb/indexer.py` 17 条（W0/W2 为主）。都在建库路径，**先不动**；
等某次建库超过 60 s 再回头看，别为条数好看去改冷路径。

## 5 明确不做（附依据）

| 不做 | 依据 |
|---|---|
| 换 rdflib/oxigraph | 无公开对比基准可引；自研在 21 万三元组下 1.8 s 已够；换库收益证明不了 |
| 上 SHACL 全套 | 现有 `ontology_check.py` 已覆盖本域约束；SHACL 的价值在多源合并，当前单域用不上 |
| 改 `evidence_kb/indexer.py` 的 17 条静态项 | 全在冷路径，建库一次的事 |
| 上 GraphRAG 替代受控查询 | CypherBench 的现实区间是 31%~72%，受控查询在我们的题面上更稳；证据在 §3 |
