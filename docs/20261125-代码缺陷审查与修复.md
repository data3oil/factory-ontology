## 1 已修（两处，均有前后实测）

### 1.1 断链门假红 25 条：只扫 `@app.*`，看不见动态挂载的路由族

`scripts/check_chainbreak.py` 用正则 `@app\.(get|post|...)` 扫 `api_server.py`，
但 12 个路由族（audit/axiom/eval/evolve/export/flows/industry/knowledge/standard/stats/trace/evidence）
是在 `api_server.py:3316-3323` 用 `importlib` + `include_router` 挂进来的，
端点声明在 `codes/routes/<family>_routes.py` 里、写作 `@router.*`。

结果：**25 条真实存在的端点被判「后端无此路由」**。门的价值在能报警，假红多了真断链就淹在噪音里。

修法：`parse_backend_routes()` 增加扫 `codes/routes/*_routes.py` 的 `@router.*`（路由族无 prefix，路径自带 `/api`）。
实测：**反向断链 25 → 0**。

### 1.2 `answer()` 入参无校验、中文空白不归一

对抗输入实测（valve 库，697 条实例）：

| 输入 | 改前 | 改后 |
|---|---|---|
| `answer(None, ...)` | `TypeError: expected string or bytes-like object` | `ValueError: 问题必须是字符串，收到 NoneType` |
| `data` 传 list / None | `AttributeError: 'list' object has no attribute 'values'` | `ValueError: data 必须是 {表名: [行dict]}` |
| `"有多少台  设备"`（中间两空格） | 暂不支持该问题 | 有 10 台设备 |
| `"有多少台\t设备"`（制表符） | 暂不支持该问题 | 有 10 台设备 |
| `"capacity_l 最大是多少"`（英文含空格） | 正常 | 正常（未受影响） |

修法：入口校验 + 中文问句去除全部空白、英文问句只折叠为单空格（避免把 `capacity l` 粘成 `capacityl`）。
其余 10 项（空串、纯标点、5000 字长串、SQL 注入串、模板注入、emoji、换行）改前即优雅拒答，未崩。

## 6 提速（2026-11-25 第二轮，CodeAgent 执行）

### 6.1 先定位，再动手

cProfile 拆三段（53 400 三元组，单问 `answer` 0.42 s）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| `parse_nt` | 0.27 s | 解析 .nt，纯 I/O + 字符串切分，未动 |
| `build_data` | 0.16 s | 三元组 → 实例字典，未动（`tail()` 500 万次调用） |
| `answer` | 0.42 s | 真热点在这一段 |
| ├ `_class_cn_aliases` | cumtime **1.30 s**（被调 336 次） | 每次 `for key, rec in data.items()` 扫全表 → O(调用数 × 表大小) |
| ├ `_resolve_entity_map` | cumtime **1.34 s** | 同上，也扫全表 |
| ├ `_field` | **46 000 次调用**，cumtime 0.93 s | 每次重拼驼峰别名（对同一 canonical 是常量） |
| └ `_enum_value_in_data` | cumtime **0.80 s** | 每次问句都全表扫 6 个候选字段重建枚举候选集 |

### 6.2 改了四处（都在 `codes/ontology_qa_v3.py`）

| # | 改动 | 为什么这么改 |
|---|---|---|
| 1 | `_data_index(data)`：类名 → 首个实例的索引，按 data 身份缓存（上限 8，FIFO） | 把 336 次全表扫变成 1 次 |
| 2 | `_class_cn_aliases` / `_resolve_entity_map` 改用该索引 | 同上 |
| 3 | `_field`：别名候选键（别名表、驼峰形态、归一化名）按 `(canonical, 词典身份)` 缓存；记录归一化视图按 `id(rec)` 分桶 + `is` 复核（上限 4096） | 驼峰拼接对同一 canonical 是常量，不该按 46 000 次调用重算 |
| 4 | `_enum_value_in_data`：候选值集合只取决于 `(data, 词典)`，按 data 身份缓存（上限 8） | 每次问句重扫全表毫无必要 |

**踩坑记录（重要）**：第一版把记录归一化缓存写成 list 线性扫，53k 三元组从 0.34 s 恶化到
**4.37 s**；把「按长度当缓存键」的写法也在设计阶段就否决了——长度会撞车、地址会复用，
命中过期数据就是答错数。最终一律 `id()` 分桶 + `is` 复核。

### 6.4 边界（必须写清，否则下次有人踩）

1. **缓存按对象身份命中，data 原地修改不会被感知**。现有调用方都是 `build_data` 出新 dict，
   所以安全；如果谁在同一个 data 上 `data[k] = ...` 加记录，枚举候选集会滞后。改数据请重建 data。
2. **缓存持有 data 引用**（这正是指针复用下仍能正确的原因），最多 8 份常驻。多库场景下
   相当于最多 8 个库的实例字典不被回收。
3. **规模边界不变**：21.4 万三元组时全链路 2.4 s，10 万以内约 1 s 内。再往上（百万级）
   该换存储/索引，不是继续加缓存。
4. **等价边界**：20 条问题的答案逐条与改前一致（`tests/probes/_opt_baseline.json` 是改前录的基线）；
   `pytest codes/tests` 串行复跑两次均 **261 passed, 2 skipped**。

> 一次 261 → 1 failed 的记录：那一轮我正在并发跑 213 600 三元组的规模探测，
> `test_api.py` 的问答被 30 s 超时打断（整轮 72.7 s vs 正常 11.8 s）。串行复跑两次全绿，
> 不是代码缺陷，但说明**并发压测时这个 API 的 30 s 超时会误伤**。
