# 代码缺陷审查与修复（2026-11-25）

对象：本仓库（v0.6.3）
方法：跑自带门 + CodeAgent 代码审查（4 个模块）+ 对抗输入探测 + 断链门交叉验证
基线：`pytest codes/tests` **261 passed, 2 skipped**；改后仍 **261 passed, 2 skipped**（无回归）

## 1 已修（两处，均有前后实测）

### 1.1 断链门假红 25 条：只扫 `@app.*`，看不见动态挂载的路由族

`scripts/check_chainbreak.py` 用正则 `@app\.(get|post|...)` 扫 `api_server.py`，
但 12 个路由族（audit/axiom/eval/evolve/export/flows/industry/knowledge/standard/stats/trace/evidence）
是在 `api_server.py:3316-3323` 用 `importlib` + `include_router` 挂进来的，
端点声明在 `codes/routes/<family>_routes.py` 里、写作 `@router.*`。

结果：**25 条真实存在的端点被判「后端无此路由」**。门的价值在能报警，假红多了真断链就淹在噪音里。

修法：`parse_backend_routes()` 增加扫 `codes/routes/*_routes.py` 的 `@router.*`（路由族无 prefix，路径自带 `/api`）。
实测：**反向断链 25 → 0**。

### 1.2 `answer()` 入参无校验、中文空白不归一

对抗输入实测（valve 库，697 条实例）：

| 输入 | 改前 | 改后 |
|---|---|---|
| `answer(None, ...)` | `TypeError: expected string or bytes-like object` | `ValueError: 问题必须是字符串，收到 NoneType` |
| `data` 传 list / None | `AttributeError: 'list' object has no attribute 'values'` | `ValueError: data 必须是 {表名: [行dict]}` |
| `"有多少台  设备"`（中间两空格） | 暂不支持该问题 | 有 10 台设备 |
| `"有多少台\t设备"`（制表符） | 暂不支持该问题 | 有 10 台设备 |
| `"capacity_l 最大是多少"`（英文含空格） | 正常 | 正常（未受影响） |

修法：入口校验 + 中文问句去除全部空白、英文问句只折叠为单空格（避免把 `capacity l` 粘成 `capacityl`）。
其余 10 项（空串、纯标点、5000 字长串、SQL 注入串、模板注入、emoji、换行）改前即优雅拒答，未崩。

## 2 新发现（门修好后才看得见的）

### 2.1 32 条后端路由没有前端入口

修好断链门后，正向断链从 19 升到 **32**——因为门现在才知道后端有这些路由。抽样核对分类：

| 类别 | 端点 | 判断 |
|---|---|---|
| 运维/鉴权 | `/health` `/metrics` `/api/version` `/api/admin/{kbs,rebuild,sync}` `/api/auth/{token,refresh,revoke,ban,unban,whoami,state,sso/status}` | 外部监控/运维用，不是死链，但应在白名单里登记，否则每次都算断链 |
| 真·无入口功能 | `/api/flows` `/api/flows/presets` `/api/flows/{id}/run` `/api/export/reverse` `/api/audit/chain` `/api/audit/decisions` `/api/audit/export` `/api/evidence/{search,status,verdict,rebuild}` `/api/industry/export` `/api/trace/forward` `/api/ontology/graph-svg` | `web/src`、`web/server` 里**零引用**（grep 实证），界面点了没有任何入口 |

这不是崩溃类 BUG，但属于「能力建了没接线」：审计链、证据检索、流程编排四块后端齐全，界面看不见。
要么补入口，要么承认它们是 API-only 并在 README 写清。

### 2.2 审查工具自己的假阳率不低（重要，影响以后怎么看它的报告）

CodeAgent 审查 4 个模块共 115 条，逐条核对下来：

| 报告项 | 实查结论 |
|---|---|
| `graph_store.py` **P0 SQL 注入风险** | **误报**。该文件所有 SQL 都是常量串（`SELECT count(*) FROM triple`）或参数化 `execute(sql, (a, b))`，无拼接 |
| `ontology_qa_v3.py` 除零风险 ×2（L1986/L2553） | **误报**。两处附近无除法；L2553 是 `max/min` 极值 |
| `cn-tokenize` P1 ×4（L211/L352/L641…） | **误报**。命中的是 `uri.split("#")`、`s.split("/")` 这类 URI 解析，不是中文分词 |
| `ontology_qa_v3.py:178` 静默 `except: pass` | **真但不严重**。有注释说明是"公共词典缺失时降级"，代价是没有日志，出问题查不到 |
| 圈复杂度 39（`ontology_graph`）、21（`write_outputs`）等 90+ 条 P2 | 真，但属风格债，不是缺陷 |

结论：**这条审查链能找「可疑形状」，判断对错必须回到代码**。假 P0 会误导优先级（这次若照单去"修 SQL 注入"，是白改）。
