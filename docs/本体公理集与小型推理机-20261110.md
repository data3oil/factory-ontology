# 本体公理集与小型推理机（2026-11-10）

## 一句话

给工厂本体加了 14 条公理和一个 400 行以内的前向推理机，纯标准库、不引 rdflib、不动既有问答链路。推理结果落在独立文件里，想用就用，不想用不影响现状。

## 为什么现在加

之前本体的定位是「轻量 JSON schema，输出 N-Triples 只是序列化」。这个定位守住了"中小厂干得动"，但也漏了一类问题：**跨表的关系答不出来**。

典型的是"这个产品用了哪些原料"。原料挂在批次上（`批次 -usesRawMaterial-> 原料`），产品挂在批次上（`批次 -producedIn-> 产品`），答案要跨两张表推一步才出来。规则引擎按字段算，答不了；模型去猜，就可能编。这类问题正适合用公理补，一条属性链就够，不需要上 OWL DL。

所以这次做的是 **L2 最小公理集**那一档，不是 L3 全导出。原来文档里"✗ 完整公理集 + 推理机、✗ 引 rdflib"这条边界没有破。

## 公理清单（14 条）

| 编号 | 类型 | 内容 |
|---|---|---|
| AX-RDFS-SUBCLASS | 类型继承 | 从图里已有的 `rdfs:subClassOf` 读，个体类型上溯，类层次传递 |
| AX-DR-* | 域值域 | 按 schema 的 `relations.from/to` 生成，每个关系一条（本次 6 条） |
| AX-C01 | 属性链 | `producedIn⁻ ∘ usesRawMaterial ⇒ hasMaterial`，产品→原料 |
| AX-C02 | 属性链 | `checkedBy ∘ producedIn ⇒ hasQc`，质检记录→产品 |
| AX-F01 | 单值 | 产品 `modelCode` 只能一个值，出现第二个报冲突 |
| AX-D01/D02 | 不相交 | 产品⊥客户、批次⊥质检记录 |
| BR-01 | 业务规则 | 质检任一项不合格 → 批次 `status=待处理` |
| BR-02 | 业务规则 | 批次待处理/隔离 → 产品 `deliveryStatus=暂停发货` |
| BR-03 | 业务规则 | 设备 `powerKw>100` → `equipmentClass=重点设备` |

公理集是数据文件：`codes/config/ontology_axioms.json`。加一条公理是改 JSON，不是改代码。

## 怎么跑

```bash
cd codes
python axiom_reason.py --nt output/valve.nt \
    --schema config/ontology_schema.json \
    --axioms config/ontology_axioms.json \
    --out-dir output/reason
```

产出四个文件，都在 `output/reason/`（该目录已被 gitignore）：

- `inferred.nt` — 只含新推出来的事实
- `closure.nt` — 原图 + 推理结果，可直接喂 `ontology_sparql.query`
- `report.json` / `report.md` — 每条新事实的依据（哪条公理、由哪几条推出）、冲突清单

## 顺手抓到的三个真问题

推理机第一次跑就撞出导出器的毛病，这些不是新写的代码造成的，是一直在那儿：

**1. 销售→产品的 30 条边全是悬空的。** 宾语写成了 `Valve_sales_P006`，真实个体叫 `Valve_products_P006`——个体 IRI 用了"引用方表"前缀，而不是"目标表"前缀。也就是说，现在从图里顺着销售记录找产品，一条都找不到。推理机按尾段唯一匹配做了内存修正（原文件没动），但这该在导出器里修。

**2. `sells` 的 domain/range 都写成了 `Valve_sales`。** schema 里明写 `Product -> Sale`。两头都写销售，意味着任何按 domain 推类型的下游都会把销售记录标成产品。

**3. `usesRawMaterial` 的 domain 写成了 `Valve_batches`，schema 说 `BatchIngredient`。** 而且数据里压根没有 `BatchIngredient` 个体，实际就是批次直连原料。

对这三处，推理机采取的是**宁可不推也不推错**：端点类型对不上就跳过该条公理并记账（report.md 的"公理端点与数据对不上"一节）。所以这次 `sells` 一条 domain/range 类型都没推——这是刻意的，不是漏了。

## 边界与限制

- 只有前向链，没有反向链、没有 `sameAs`、没有基数约束求解、不做一致性求解。撞到矛盾只报告，不修。
- 属性链只支持"沿两条关系走一步"这种形态，不做任意长度路径。
- 业务规则是"条件 + 沿一条关系传播 + 赋值"的固定形态，不是通用规则引擎。真要通用，那是另一个项目。
- 推理结果不写回 `output/valve.nt`，也不进问答主链路。目前是旁路能力。
