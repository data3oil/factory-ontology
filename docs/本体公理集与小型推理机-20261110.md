# 本体公理集与小型推理机（2026-11-10）

## 一句话

跨行业种子 + 每个库一份可编辑的公理集 + 一个零依赖前向推理机，接到问答链路上：问到跨表关系时用推导事实作答，答案带依据。前端有「公理与推理」页，能改、能存、能跑、能试问。

## 为什么不是"给阀门写死一套"

远端这个项目是跨行业的（阀门、食品、能源站、机床、船舶…）。公理集要是绑死 `Valve_products`，换个库就是废的。

所以分两层：

- **种子**（`config/axioms/_seed.json`）：只认「角色」——哪张表是产品、批次、原料、质检、设备。判据是表名里的词（product / batch / material / ingredient / qc…），不写死任何一行的表名。
- **分库公理集**（`config/axioms/<kb>.json`）：种子按该库数据生成一遍，之后就以这份文件为准，用户可改。

生成时最有用的不是角色识别，是**沿数据里真实存在的边找路径**。种子不去猜"应该有什么边"，而是看这个库里实际有什么：产品能不能经批次走到原料，几步走到。走不通就跳过并在面板上写清楚跳过了什么。

实测两个行业：

| 库 | 产品→原料路径 | 规则 |
|---|---|---|
| valve（阀门） | `producedIn⁻ → usesRawMaterial`（2 步） | 质检不合格→批次待处理 |
| food（食品） | `produces⁻ → belongsToBatch⁻ → usesRawMaterial`（3 步） | 同上，属性名从数据取 |

同一个种子，两个行业都出得来，路径长度不同是因为数据长法不同。

## 四层结构

```
config/axioms/_seed.json      角色定义 + 链模板 + 质检规则模板
        ↓ generate(kb)
config/axioms/<kb>.json        该库公理集（人可改，前端改的就是它）
        ↓ axiom_reason 前向链跑到不动点
output/reason/<kb>/closure.nt  原图 + 推导事实
        ↓ axiom_service.answer
/api/ask 的 axiom 引擎          答案 + 依据（哪条公理、由哪几条推）
```

## 公理有哪几种

| 类型 | 作用 | 例子 |
|---|---|---|
| 类型继承 | 个体类型沿 subClassOf 上溯 | 产品也是 BusinessObject |
| 域值域 | 按 schema 的 from/to 补类型 | 但端点对不上就跳过，不硬推 |
| 属性链 | 跨表关系 | `产品→批次→原料 ⇒ hasMaterial` |
| 单值 | 编号类属性多值即冲突 | 型号编码、执行标准 |
| 不相交 | 类之间不能同时成立 | 产品⊥客户、批次⊥质检 |
| 业务规则 | 条件 + 沿一条关系 + 赋值 | 质检不合格→批次待处理→产品暂停发货 |

公理文件里每条都带 `ask`：中文问法。这是问答接入的接口——问句里出现这些词，且出现了实体，才走公理引擎；否则一律交回原链路。不猜、不抢。

## 前端：公理与推理页

左侧「建本体与演进 → 公理与推理」。这一页是闭环的自检台：

- 顶部统计 + **按种子重新生成 / 跑推理 / 保存**
- 角色识别结果与「种子跳过了什么」，一眼能看出这个库认没认对
- 表单编辑：属性链（可加步、勾反向）、业务规则（当/则/沿哪条关系）、单值、不相交；也可切 JSON 原文直接改
- 推理结果：新增条数、各公理贡献、端点不符、规则改写既有状态的清单、推导样例（带依据）
- **试问**：走正式 `/api/ask`，显示 mode / 引擎 / 置信 / 证据。看到 mode=axiom 就说明闭环通了

保存会先备份旧文件（`.bak_<时间戳>`），结构不合规直接拒绝，不写半成品。

## 问答链路怎么接的

`_ask_impl` 里加了一个 `axiom` 引擎，两处入口：

1. 规则引擎答上了但**没有行级证据**（只有话术）时，先让公理试；
2. 规则引擎直接没答上时，也先让公理试。

命中就进 fusion，`source=axiom` 与 `rule/logical` 同级（确定性），置信 high。不命中返回 None，链路原样往下走，行为不变。

为什么不是永远优先：\"有多少台设备\"这种就该归规则引擎，公理不该抢。公理只在问法命中 `ask.terms` 且找到实体时才开口。

实测（valve 库）：

```
P004 用了哪些原料   → mode=axiom  气动球阀 Q641F-40P 的用料：阀体铸件、阀杆、密封圈、螺栓（4 项）
R001 被哪些产品用到 → mode=axiom  阀体铸件 关联到：球阀 Q41F-16P…（4 项，反向）
哪些产品暂停发货     → mode=axiom  按公理 BR-02，暂停发货的有：…（3 个）
P004 的质检记录      → mode=axiom  Q023（1 项）
有多少台设备         → mode=rule   有 10 台设备（公理不插手）
```

## 顺手抓到的三个导出器问题

推理机第一次跑就撞出来的，不是新代码造成的：

1. **销售→产品的 30 条边全悬空**。宾语写成 `Valve_sales_P006`，真实个体是 `Valve_products_P006`——个体 IRI 用了「引用方表」前缀而不是「目标表」前缀。顺销售记录找产品，一条都走不通。
2. **`sells` 的 domain/range 都写成 `Valve_sales`**，schema 明写 Product→Sale。
3. **`usesRawMaterial` 的 domain 写成 `Valve_batches`**，schema 说 BatchIngredient，而数据里没有 BatchIngredient 个体。

对这三处，推理机**宁可不推也不推错**：端点类型对不上就跳过该公理并记账。所以 `sells` 一条类型都没推，是刻意的。悬空引用按尾段唯一匹配在内存里修正（原文件不动），并在报告里列出。

## 边界

- 只有前向链，没有反向链、sameAs、基数求解；撞到矛盾只报告不修。
- 属性链是"沿已有边走一段"，不支持任意长度正则路径。
- 业务规则是固定形态（条件 + 一条关系 + 赋值），不是通用规则引擎。
- 推理产物不写回 `output/valve.nt`；改写既有状态（如批次原本"已入库"）会列出来让人判断，不静默覆盖。
- 种子认不出的行业，生成的是空公理集 + 一条跳过原因，不会硬编。
