# 工厂本体审查

## 一、结论

门是干净的：14 个自检门全过，`pytest` 261 passed / 2 skipped，边界自检违规 0，问答回归 331 题零编造。**问题不在这条被门覆盖的主链路上**，而在门没覆盖的两处：

1. **实例名当实体用时，守卫失配，答出与问题无关的计数**（P0，已复现，会给用户一个确定的错数字）。

## 三、P0：实例名守卫失配，错答确定数字

**现象**（同一份地震库，同一问法，只换实体）：

| 问句 | 实际回答 | 判定 |
|---|---|---|
| 塔里木三维区块B的炮点数是多少 | 符合条件共 2 条 | ✗ 与问题无关的计数 |
| 塔里木三维区块B的炮点数 | 暂不支持该问题 | ✗ 数据在库（shotpoints=12000） |
| 鄂尔多斯三维区块A的炮点数 | 暂不支持该问题 | ✗ 数据在库（8500） |
| 测线塔里木三维区块B的炮点数 | 塔里木三维区块B的炮点数：12000 | ✓ |
| 四川二维测线C的炮点数 | 四川二维测线C的炮点数：3000 | ✓（只因为实体名里自带"测线"） |

**根因（两层，同一处）**

`codes/ontology_qa_v3.py:2601` 的守卫 `_named_entity` 只认两种形态：

1. 字母段+数字段相邻的 ID（`AC-01` / `AC01` / `AC_01`）；
2. `get_entity_cn2uri()` 里的中文名，而这份索引**只有 8 个类名**：

```
索引条数 8
  塔里木三维区块B  in idx: False
  四川二维测线C   in idx: False
  测线          in idx: False
  设备          in idx: True
```

于是「实例名 + 的 + 属性 + 是多少」这种最自然的问法，守卫判成"没点名实体"，落进 `_value_filter_count` 兜底，把实体名当成一个"取值"去数行数，得到 2。

同一份索引缺口也解释了「暂不支持」：属性过滤分支要靠类名词锚定实体，实体名本身不在索引里，没有"测线"三个字就锚不上。

**影响**：这是对外可信度问题，不是性能问题。用户问具体对象给不出答案可以接受，给出一个确定的错数字不可接受。

**修法（建议）**

1. 建实例名索引：从 `data` 的实例属性里取显示名（`lineName` / `name` / `_display_name`），构成长度 ≥3 的集合，供守卫与实体解析共用。10 万级实例不要线性 `in` 扫描，用首字分桶（`{首字: [name...]}`）后桶内比对，规模上仍是毫秒级。
2. 守卫改为：问句命中任一类名 **或** 任一类实例名 → 不进取值过滤兜底。
3. 属性过滤分支的实体解析复用同一索引，去掉"必须有类名词"的隐含前提。
4. 回归：把上表 5 条问法写成探针，断言 1、2、3 行分别给出 12000 / 12000 / 8500，第 4、5 行保持原答案。

## 四、P1：人在环确认不校验候选存在

`codes/ontology_evolve.py:323` 的 `confirm()` 只判 `name` 非空：

```python
if not name:
    return False, "候选名不能为空"
```

名字不在 pending 里也照并词典、版本 +1、写快照。`_PENDING` 只在事后做剔除（347 行），从未校验"这个名字本来就在待确认区"。后果是人在环退化为"随便加词"，并且会写脏词典与版本历史。

修法：进入写路径前断言 `name ∈ [c.get("name") for c in pending]`，不在就返回 `False, "候选不存在或已处理"`。这条技能文档里已记为待修，代码里仍未落地。

## 五、P2：契约与配置卫生

1. **未命中仍回传 evidence**。`api_server.py:2140` 明确把 hybrid 候选放进 evidence（注释说"实体线索仍留在 evidence 里可溯源"），但接口文档与 `factory-ontology-qa` 技能都写"全部答不上时 evidence 空数组"。实测 `SEIS-001 是什么` 返回 `no_basis=true` 且 evidence 5 条。两种做法都说得通，**必须择一并写进契约**；现状是前后端按不同理解各写各的。
2. **`active_ontology.json` 的 schema 指向 valve**：`{"kb":"seismic", "nt":"output/seismic.nt", "schema":"config/ontology_schema_valve.json"}`。若 schema 是通用模板应当改名，若真是阀门的，则地震库的实例校验在用错模板（当前 SHACL 门通过，说明未触发约束）。
3. **无鉴权端点**：`/api/app-config`、`/metrics`、`/health` 匿名可取。内容分别是品牌/示例问题、请求计数、健康状态，不含业务数据，属可接受暴露；但 `/api/ontology/graph-svg` 直接读 `docs/diagrams/*.svg`，交付前应确认该图不含甲方信息。

## 六、优化空间

| 项 | 现状 | 判断 |
|---|---|---|
| 单问答延迟 | p50 0.31s / p95 0.56s（规则档） | 已经够快，不必优化 |
| 并发 | 8 并发 1.29s、0 失败；执行器 4 worker、超时 30s | 8 并发内够用；超过 4 个慢问句会排队，压测到 32 并发再谈扩容 |
| 大图加载 | 技能记录 20 万实体 30.5s 建库 / 14.1s 加载 | **真正的规模化瓶颈**，与本次缺陷无关，优先级低于 P0 |
| 缓存 | 按 nt/词典文件指纹失效，正确 | 不动 |
| 全局状态 | `graph/labels/vi/rev/QDATA` 在多处被整体重赋 | 重建与问答并发时存在短暂不一致窗口，建议后续改成"构建新上下文再原子替换" |

## 七、不做什么

- 不为 P0 改匹配算法（`_find_enum` 那套源头修法已稳定，命中率 72.7% 起），只在"实体是否被点名"这一层补索引。
- 不因为一条错答就推翻规则引擎整体排序策略，改动限定在守卫与实体解析两处。
- 不动无鉴权端点，除非交付对象要求全站鉴权（那是策略决定，不是缺陷）。
