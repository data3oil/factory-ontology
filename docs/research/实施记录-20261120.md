# 实施记录：开源本体优化（2026-11-20）

对应方案 `docs/research/开源本体技术路线-20261120.md`。逐项给出做了什么、实测数字、以及没做到的部分。

## P0-3 规模化：SQLite 图存储回归

- 新增 `codes/graph_store.py`：三元组落库（表 + 节点 + 值索引），`load()` 返回与
  `graph_rag.build_graph` 同构的四元组，调用方零改动。
- 关键优化：索引放到插入之后建，构建期 `synchronous=OFF`。50k 实体（25 万三元组）实测：
  - 解析 .nt 建图 1.10s
  - SQLite 落库 2.78s
  - SQLite 加载 3.89s
  优化前分别是 1.10s / 28.70s / 14.64s。
- 边界：加载仍比直接解析慢（0.3x），因为 SQLite 读取 + Python 组装有固定开销；
  小库仍应走内存图。20 万实体（100 万三元组）本轮未跑完，脚本支持 `--n 200000`，
  但当前机器上解析阶段被中断，未取得数字。

## P0-1 IOF 映射

- 新增 `codes/config/iof_mapping.json`：8 个业务实体映射到 IOF Core 概念，全部 closeMatch/relatedMatch，
  差异写在 note 里（例如设备在 IOF 是 EquipmentRole 角色，我们在台账里固化成类）。
- 新增 `codes/config/iof_core_classes.txt`：从 `core/Core.rdf`（MIT）抓取的 90 个类名快照，离线可校验。
- 新增 `scripts/verify_iof_mapping.py`：IRI 前缀、类名存在性、重复映射、覆盖率（只算有物理表的业务实体）。
  实测 8/8，覆盖率 100%。

## P0-2 逻辑一致性

- 新增 `codes/logic_check.py`：主键唯一、单值关系、链式公理无环、不相交类；未声明的检查标 SKIP 而不是通过。
- 在 `ontology_schema_valve.json` 增加 `disjoint` 三条（产品/客户、设备/原料、批次/销售），
  C4 从 SKIP 变为真实执行并通过。
- 已加入 `scripts/run_all_gates.py` 的 GATES。
- 说明：项目原有 `verify_shacl.py`（SHACL 子集校验）、`verify_iri_integrity.py`、`verify_oops.py`，
  本次是补"逻辑层"而不是取代。

## P1-1 查询规划（条件计数 / 属性枚举 / 实体记录数）

- 在 `codes/ontology_qa_v3.py` 的 `answer()` 最前面加三条句式解析，位于关系查询之前：
  - `X 中 Y 为 Z 有多少条` → 按属性过滤计数；属性被建模成关系时按目标 IRI 尾段兜底。
  - `X 的 Y 有哪些` → 枚举该属性的取值。
  - `X 有多少条记录` → 计实例数。
- valve 评测（44 题）：命中率 84.1% → **88.6%**，filter 62.5% → **88%**，p50 0.31s。
- 剩余 5 题全部同因：配料/外键被建模成关系，本体里没有逐行实例节点，无法回答"批次原料有多少条记录"这类
  按行计数的问题。这是建模粒度问题，不靠改问答能修。

## P1-2 融合：RRF

- `codes/fusion.py` 新增 `rrf_rank()`：按来源分组做倒数排名融合（k=60），同一答案跨来源累加分。
- 未默认启用到 `/api/ask` 主链路，避免影响既有 88.6% 基线；作为可选能力与测试覆盖。

## P1-3 可复跑 benchmark

- 新增 `scripts/build_sparql_bench.py`：SPARQL 由代码生成，问句由模板生成，六类模式
  （linear / two_hop / branch / filter / reverse / type）。
- 实测产出 57 题（valve，6 类齐全，每类前 10 条执行验证），落在 `codes/output/bench/sparql_bench_valve.jsonl`。
- 未达 500 题：two_hop 在自研 SPARQL 子集里是笛卡尔式 join，单查 1s 以上；且 `LIMIT/UNION/聚合`
  子集不支持。要到 500 题，需要先给引擎加索引或换 Oxigraph 后端。

## P2 AAS 导出
