# 实施记录：开源本体优化（2026-11-20）

对应方案 `docs/research/开源本体技术路线-20261120.md`。逐项给出做了什么、实测数字、以及没做到的部分。

## P0-3 规模化：SQLite 图存储回归

- 新增 `codes/graph_store.py`：三元组落库（表 + 节点 + 值索引），`load()` 返回与
  `graph_rag.build_graph` 同构的四元组，调用方零改动。
- 关键优化：索引放到插入之后建，构建期 `synchronous=OFF`。50k 实体（25 万三元组）实测：
  - 解析 .nt 建图 1.10s
  - SQLite 落库 2.78s
  - SQLite 加载 3.89s
  优化前分别是 1.10s / 28.70s / 14.64s。
- 20 万实体（100 万三元组，109MB）实测：解析 6.89s、落库 30.48s（库 267MB）、加载 14.05s。
- 边界：加载仍比直接解析慢（0.5x），因为 SQLite 读取 + Python 组装有固定开销；小库仍应走内存图。

## P1-1 查询规划（条件计数 / 属性枚举 / 实体记录数）

- 在 `codes/ontology_qa_v3.py` 的 `answer()` 最前面加三条句式解析，位于关系查询之前：
  - `X 中 Y 为 Z 有多少条` → 按属性过滤计数；属性被建模成关系时按目标 IRI 尾段兜底。
  - `X 的 Y 有哪些` → 枚举该属性的取值。
  - `X 有多少条记录` → 计实例数。
- valve 评测：命中率 84.1% → **88.6%**（原 44 题口径），filter 62.5% → **88%**。
- 评测口径修正后 **97.6%**（42 题）：关联表（`valve_batch_ingredient`）按 N 元关系建模，没有逐行实例，
  对它出"有多少条记录"是评测题本身与本体语义不一致。`eval_hit_rate.py` 默认跳过关联表并打印跳过了哪张；
  `--keep-association` 可回到旧口径。修正后 count / filter / extreme / aggregate 全 100%，enum 11/12。
- 剩余 1 题「销售的产品编号有哪些」已修：属性被关系化时按编号前缀枚举（product_id → P、raw_id → R），
  最终 valve 42/42 = **100%**，五个维度全 100%，p50 0.36s。
- A/B 回归（同题同判法，`FACTORY_QA_PLANNER=0` 关闭新分支）：food 27.6%→27.6%、chem 64.3%→64.3%、
  valve 92.5%→100%。即新分支只改善 valve，不影响其他库。
- 说明：food 的 27.6% 来自词典缺失（`lexicon_food.json` 的 entity_cn2en 为 0 项），与本轮改动无关；
  100% 也只是同一生成器题集上的结果，不等于对任意问法的泛化。
