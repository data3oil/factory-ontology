# 工厂本体开源：技术路线分析与优化方案

日期：2026-11-20。范围：`D:\factory-ontology`（v0.6.1，Apache-2.0）。检索覆盖 2024 至 2026 年公开论文与工业标准，链接在文末。

## 一、结论

这个项目的差异化不在"本体"三个字，在三点：零依赖离线、答案带证据、schema 驱动换厂只换域。
这三点恰好是 2024 至 2026 年 GraphRAG 与本体工程论文都没有解决的工程侧问题，所以路线是对的。

短板也清楚：没有上层本体对齐、没有标准推理与一致性检查、规模化断档、缺公开 benchmark。
这四条不补，项目会被归到"又一个轻量图谱问答 demo"；补上，才站得住"工业本体底座"。

## 三、论文与标准图景

**1. 图增强检索（GraphRAG 一系）**

- GraphRAG（arXiv:2404.16130）提出实体图 + 社区摘要，解决全局性问题。
- LightRAG（arXiv:2410.05779，EMNLP 2025）用双层检索与增量更新，把建图成本压下来。
- KAG（arXiv:2409.13731，蚂蚁/阿里）针对专业域：数值、时间、专家规则这些"向量相似度不敏感"的东西，靠 KG 与向量双向增强，并提出逻辑形式求解。
- 综述（arXiv:2501.13958）把这一系归纳为"图结构表示 + 图检索 + 结构感知生成"三段。

对我们的意义：我们的规则问答在"是什么、有多少"上比它们强（确定性、零幻觉），但在多跳与全局问题上弱。融合层已有，缺的是社区摘要与增量索引。

**2. LLM 与结构化数据交互**

- StructGPT（arXiv:2305.09645，EMNLP 2023）：把问题按 schema 分解成子问题，再逐步读取结构化数据，零样本即可。
- Think-on-Graph（arXiv:2307.07697，ICLR 2024）：LLM 作为 agent 在图上做 beam search，9 个数据集中 6 个取得 SOTA，且免训练。

对我们的意义：我们的 filter 分支只有 25% 到 75%，正是"缺分解"。把规则分支改成"意图 + 槽位 + 图遍历计划"三段，比继续打补丁干净。

**3. 本体工程自动化**

- LLMs4OL（arXiv:2307.16648）：零样本 LLM 做术语分类、分类体系发现、非分类关系抽取，结论是"基础模型不足以承担本体构建，微调后可当助手"。
- OLLM（arXiv:2410.23584）：端到端生成分类骨架，配套语义与结构相似度指标。
- Journal of Web Semantics 2025（doi:10.1016/j.websem.2025.100862）与系统综述都指出：模块化本体 + 人在环，是当前可落地形态。

对我们的意义：我们"schema 驱动 + 人在环确认"的路线有论文背书，不必追全自动。但要把"人在环"做成可审计的确认记录，否则会被质疑为人工标注。

**4. 工业标准与标准推理**

- IOF Core Ontology：以 BFO 为上层，面向数字制造，已被 ISO/IEC 21838-2 体系接纳（NIST 文档）。
- Semantic Asset Administration Shell（arXiv:1909.00690）：把工业 4.0 的 AAS 数据模型 RDF 化，并验证轻量设备也能承受语义化开销。
- ELK（CEUR Vol-858）：OWL 2 EL 专用推理机，SNOMED CT 在普通硬件上 10 秒内分类完。

对我们的意义：客户一旦问"你们本体和 IOF/AAS 什么关系"，现在答不上来。而 AAS 是德系与汽车供应链的硬要求，我们已有 `aas_example.nt`，只差一步。

## 四、差距（每条都有依据）

1. **无上层本体对齐。** schema 的 38 个实体是表结构映射，没有 BFO/IOF 锚点。后果是跨企业、跨系统无法互操作，也无法复用 IOF 的已有定义。
2. **推理不是标准 entailment。** 17 条自研公理能推业务规则，但没有 OWL 2 语义、没有一致性检查。本体写错（如类既不相交又有共同实例）系统不会报。
3. **查询理解缺分解。** 规则分支 86% 已是好成绩，但 filter 25% 到 75% 说明复杂约束没被拆开。StructGPT 与 ToG 都证明"分解 + 图上游走"能补这块。
4. **GraphRAG 只有检索，没有全局视角。** 缺社区摘要、缺增量索引，多跳与"整体趋势"类问题会退化成片段拼接。
5. **规模断档。** 10 万实体以上没有实现，`规模化.md` 已承认。企业台账（MES/ERP 全量）很容易过线。
6. **评测不可对外比较。** 自有 5 类问题 + 确定性判分很扎实，但没有公开 benchmark 口径，外部无法复核，也难以发论文。

## 五、优化方案

### P0（两周，补硬伤）

**P0-1 IOF 映射层（不动现有 IRI）**

新增 `config/iof_mapping.json`，把 8 到 10 个核心类（Equipment、Product、Batch、Process、Quality、Material、Customer、Sale）映射到 IOF Core 的对应类，附 `skos:closeMatch` 与依据说明。加一个探针校验映射目标存在、无环。
论文依据：IOF Core / BFO 分层架构。

**P0-2 一致性检查三项，进 CI**

不相交类不得有共同实例；单值属性不得多值；链式公理不得成环。纯标准库实现，输出与 `axiom_reason.py` 同格式。
论文依据：ELK 的 OWL 2 EL 可处理范围；不一致检测是本体工程底线。

**P0-3 规模回到 10 万到 100 万**

恢复 SQLite 持久化图（邻接表 + 类型索引），保留内存图作为小库默认档；给出 20 万实体的加载与查询基准，写进 `规模化.md`。这是企业交付门槛，不是优化项。

### P1（三到四周，补能力）

**P1-1 查询规划器 v2**

把规则分支重构成三段：意图识别（count/enum/extreme/aggregate/filter/多跳）→ 槽位抽取（实体、属性、约束、比较符）→ 执行计划（图遍历或聚合）。目标：filter 从 25% 到 75% 提到 85% 以上，其余四类不掉。
论文依据：StructGPT 的分解式读取；ToG 的图上 beam search（多跳分支）。

**P1-2 检索融合升级**

在 `fusion.py` 加 RRF（倒数排名融合）与轻量社区摘要（按类型/域聚类，生成 1 到 2 句摘要，缓存）。只对多跳与全局问题启用，保持确定性问答秒回。
论文依据：GraphRAG 的社区摘要；LightRAG 的双层检索与增量更新。

**P1-3 可复跑 benchmark**

按 Build2SPARQL（arXiv:2610.00224）的做法：SPARQL 由图遍历代码生成并验证，LLM 只生成自然语言问句。产出 500 题（6 类模式 × 5 种问法），人工抽检 50 题。这样"准确率"才可对外复核。
论文依据：Build2SPARQL 的 pipeline 设计与人工验证口径。

### P2（按需）

- AAS 导出：把 `aas_example.nt` 扩成 AAS submodel 导出，对接工业 4.0 客户。依据 Semantic AAS。
- 可选 SPARQL 1.1 端点：Oxigraph 插件，零依赖档保持默认。依据 ELK/Jena 生态的工程实践。
- 本体学习：只做"候选类/属性建议"，人工确认后入库，不做全自动。依据 LLMs4OL 的结论。

## 六、开源策略

- 许可证保持 Apache-2.0，NOTICE 随包；对外统一口径"算法原子开源，闭源侧编排"。
- 社区抓手只有两件：IOF 对齐（让懂本体的人愿意提 PR）与可复跑 benchmark（让质疑的人能自己验）。
- 风险项：`codes/output/ai4i.nt` 19MB，来源是 AI4I 工业数据集，需核对其许可与再分发条款，不能默认可以随仓库分发。
