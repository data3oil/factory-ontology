## 三条可用的结论（原文判定）

**结论 1｜本体建模配得上一级菜单，前提是它承载「持续变更的资产」且自带发布语义。**
- 一级：Palantir Ontology Manager（配 branches + proposals 的 PR 式审批）、Stardog（Designer + Studio.Models 双角色）、华为云 KG（本体管理做进控制台）。
- 收纳：腾讯云 GraphRAG 把 schema 放在「知识库→知识图谱」的设置步骤里；Neo4j 塞进 Workspace（sketch→preview→import）；Cognite 干脆没图形入口，用 YAML + CI。
- 判据：只改一个 TTL 文件 → 属「知识库配置」；要长期演进、多人改、可回溯 → 应是一级，并且必须同时有 draft/publish/版本，否则就是 demo 级菜单。

**结论 2｜「编排」不是建模的附属页，更不是探活页。叫得上「编排」的一级菜单，背后都有执行引擎。**
- 正向：Palantir Automate（条件 + 效果 + 执行身份 + 影响评估）、Databricks Lakeflow Jobs（job/task/trigger/分支循环）、dbt deploy jobs。
- 反向：GraphDB / Stardog / Neo4j / Cognite 都没有把「编排」做成一级菜单，因为没有引擎或引擎属于 CI/调度系统。
- 对本仓库：只探测外部 `:8010` 的「本体编排」**不满足一等菜单标准**——没有执行、没有运行历史、没有产物，本质是外部源的健康检查。应降级为「设置 → 系统/服务状态」的一个诊断项，或随数据接入一起出现；不上菜单。

**结论 3｜商业产品把 build 与 consume 做成两套界面，菜单顺序是「业务入口在前、建模在后、编排归运维」。**
- Palantir：建模在 Ontology Manager，业务在 Object Explorer（官方称 "geared towards less technical users"）与 Workshop（"for operational users"）。
- Stardog：建模 Designer/Studio，消费 Explorer + Voicebox（自然语言问答）。
- Neo4j：建模 Workspace，消费 Bloom 的 Perspective（按业务域裁剪可见性）。
- 含义：菜单至少三层——「问答/应用」（业务用户，不出现 OWL/IRI 等工程词）、「本体建模」（建模者，带发布）、「数据与集成/系统状态」（运维，放 :8010 这类探活）。

## 与知识库问答类 13 个产品的共性（摘自姊妹篇）

1. 知识库几乎总是一级菜单（Dify/MaxKB/RAGFlow/Coze/千帆/方舟/百炼；例外 Notion）。
2. 「数据接入」极少单开一级，多折叠进知识库创建向导或管理端连接器（唯一例外百炼的「数据接入」分组）。
3. 模型配置被降级为基础设施（Dify 集成→模型供应商、AnythingLLM Settings）。
4. 编排独立成一级且定位为「应用的实现方式」，知识库只是其中的检索节点。
5. 成员/权限统一收进工作空间或管理后台，与业务菜单物理分开。
6. 评测/监控自成一组，与搭建分离；轻量产品退化为库内命中测试。
7. 管理端与使用端二分，是 To B 成熟度标志（Glean、乐享、MaxKB、Coze）。
